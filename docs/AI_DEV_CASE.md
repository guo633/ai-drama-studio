# AI 辅助开发案例 — AI Drama Studio

> 本文档记录本项目如何使用 AI 工具（Claude Code / Cursor / Copilot 等）辅助开发，
> 以及人对 AI 产出的审查与修正过程。可直接作为简历投递要求的「AI 开发案例」附件。

## 一、项目背景

目标岗位要求「会用 AI 工具辅助开发、有 Prompt 编写经验、懂 Skill」。本项目本身
就是一个 AI 内容应用，开发过程也全程与 AI 协作 —— 做的东西和做的方式互相印证。

## 二、AI 在各环节的实际使用

| 环节 | AI 做了什么 | 我做了什么（人工把关） |
|---|---|---|
| 架构设计 | 生成 FastAPI 分层骨架方案（routers/models/pipeline） | 评审后砍掉过度设计，保持 MVP 最小闭环 |
| Prompt 编写 | 起草五步流水线模板初稿 | 逐条加入领域约束：前三集爽点节奏、钩子格式、字数与格式对齐行业标准 |
| 业务代码 | 生成 JWT 认证、CRUD、后台任务样板 | 审查安全细节：PBKDF2 迭代次数、token 过期、数据按用户隔离 |
| Bug 修复 | 定位「`db.get` 按主键查询而非 step 字段」的逻辑错误 | 验证修复并回归测试全部接口 |
| 文档 | 输出 README 与本文档框架 | 补充真实的踩坑记录（见下） |

## 三、典型踩坑记录（AI 产出必须人工验证的实例）

1. **`db.get(PromptTemplate, key)` 查不到模板**
   AI 初版代码用 `db.get` 按「step 字段」查记录，但 `db.get` 只接受主键。
   测试创建短剧时流水线直接抛「缺少模板」。修正为
   `db.query(PromptTemplate).filter_by(step=key).first()` 并补回空值校验。
   **教训**：AI 生成代码中的 ORM API 语义需要逐个核对，不能凭表面可读性信任。

2. **后台任务与会话生命周期**
   生成流水线在 `BackgroundTasks` 中执行，不能复用请求级的 DB 会话
   （请求结束会话即关闭）。解决方案是流水线自建 `SessionLocal` 并在
   `finally` 中关闭，每步完成即 commit，异常时把失败状态落库。

3. **演示模式的取舍**
   面试 Demo 不能依赖付费 API Key。设计上让 `llm.chat` 在无 Key 时返回
   确定性演示文案，整条流水线照常推进 —— 既保证随时可演示，也把真实
   LLM 调用收敛在一个函数内，配置 Key 即切换，零代码改动。

## 四、我的 AI 协作方法论

1. **先架构后代码**：让 AI 出方案，人先评审边界（哪些模块值得抽象、哪些是过度设计），再动手
2. **Prompt 当产品做**：约束写进 Prompt（格式/字数/节奏），而不是事后修 —— 本项目的模板编辑器就是这个方法论的产物
3. **不信任，先验证**：AI 代码必须过一遍接口级测试（注册 → 登录 → 创建 → 轮询 → 导出全链路 curl 验证）
4. **把踩坑写回文档**：每次 AI 出错都沉淀成记录，形成个人知识库 —— 这也是「Skill」思维
